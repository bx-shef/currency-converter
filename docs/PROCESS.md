## 0. Настройка

Делается один раз. Три части: зарегистрировать приложение в портале, задать переменные,
подготовить сервер.

### 0.1. Регистрация приложения в портале Bitrix24

С этого начинается всё остальное — пока приложения нет в портале, ему некуда устанавливаться.

В портале: **Разработчикам → Иное → Локальное приложение**.

| Поле карточки приложения | Значение |
|---|---|
| Путь приложения (Application URL) | `https://<домен>/` |
| Путь для первоначальной настройки (Installation URL) | `https://<домен>/install` |
| Права (scopes) | `user_brief`, `im`, `placement` |

Права продублированы в коде — `app/config/b24.ts` (`B24_REQUIRED_SCOPES`). Если меняете
набор прав, менять надо **в двух местах**: в карточке приложения и в коде.

Дальше портал сам откроет `/install`, и страница установки зарегистрирует виджет — что там
происходит, описано в [§5](#5-установка-в-портал-bitrix24).

### 0.2. Переменные приложения

Все публичные переменные **запекаются в бандл при сборке** (у нас статика), поэтому
передаются аргументами сборки Docker, а **не** через `environment:` в compose — иначе они
просто не доедут до готовой страницы.

| Переменная | Зачем | Обязательна |
|---|---|---|
| `NUXT_PUBLIC_SITE_URL` | абсолютный адрес сайта; из него строится адрес обработчика виджета при установке в портал | **Да** для прода — без неё `/install` откажется регистрировать виджет и покажет ошибку (адрес обработчика обязан быть абсолютным) |
| `NUXT_PUBLIC_YANDEX_COUNTER_ID` | счётчик Яндекс.Метрики | Нет (пусто → статистика просто не собирается) |
| `NUXT_PUBLIC_COMMIT_SHA` | коммит сборки, показывается в подвале ссылкой | Нет (пусто → «сборка dev»). В CI подставляется автоматически |
| `NUXT_PUBLIC_MARKETPLACE_URL` | ссылка на листинг Маркета в промо-карточке | Нет (пусто → константа `MARKETPLACE_URL` из `app/utils/site.ts`) |
| `NUXT_PUBLIC_AUTHOR_NAME` / `_URL` | автор в подвале | Нет |

**Где лежат значения:** GitHub → Settings → Secrets and variables → Actions.
`NUXT_PUBLIC_YANDEX_COUNTER_ID` — в **Secrets**; остальные — в **Variables** (значения не
секретные, они всё равно попадают в публичный бандл). `NUXT_PUBLIC_COMMIT_SHA` заводить не
нужно, CI берёт его из номера коммита сам.

Сборка **падает специально**, если `NUXT_PUBLIC_YANDEX_COUNTER_ID` задан, но это не число —
чтобы битый счётчик не запёкся в бандл.

### 0.3. Сервер

```
/home/<user>/<project>/
├── docker-compose.prod.yml
├── docker-compose.nginxproxy.yml   # только если nginx-proxy ещё не развёрнут
├── .env.prod                        # НЕ в git: DOMAIN, LETSENCRYPT_EMAIL
└── Makefile
```

**Git на сервер не клонируется** — файлы качаются напрямую:

```bash
mkdir -p /home/<user>/<project> && cd $_
BASE="https://raw.githubusercontent.com/bx-shef/currency-converter/main"
for f in docker-compose.prod.yml Makefile .env.prod.example; do curl -fsSLO "$BASE/$f"; done
cp .env.prod.example .env.prod && nano .env.prod   # заполнить DOMAIN и LETSENCRYPT_EMAIL
```

Обновление файлов на сервере — тем же `curl -fsSLO`, без `git pull`.

Чек-лист первого запуска:

- [ ] DNS A-запись домена указывает на сервер (`dig +short <домен>`) — **до** первого старта
      выдачи сертификатов, иначе Let's Encrypt закеширует отказ на час
- [ ] docker-сеть существует и её имя совпадает с указанным в compose (`docker network ls`).
      Имя историческое и на разных серверах разное. Если сети нет — `make init-network`
- [ ] nginx-proxy запущен (`docker ps | grep nginx-proxy`). **Если он уже стоит — второй раз
      не поднимать**, см. предупреждение ниже. Если его правда нет — `make init-nginxproxy`
- [ ] `.env.prod` заполнен
- [ ] `make prod-up` отработал; `docker ps` показывает приложение **и** Watchtower
- [ ] `curl -I https://<домен>` → `200`, TLS валиден

> ⚠️ **Сервер общий с другими сайтами.** Не поднимайте nginx-proxy второй раз, если он уже
> работает: порты 80 и 443 заняты, и упадёт **весь сервер**, а не только этот проект.
> Так же не пересоздавайте docker-сеть «с правильным именем» без подтверждения владельца —
> контейнеры соседних сайтов останутся в старой сети и получат 502.

## 1. Разработка

```
ветка от main → правка → pnpm check (зелёный) → PR
```

- **Ветка от `main`.** В `main` напрямую не коммитим.
- **Перед пушем — `pnpm check`** (это `lint && typecheck && test`). Те же проверки гоняет CI,
  поэтому красный `check` = красный CI. Если правили зависимости — ещё и `pnpm audit`
  (CI валит сборку на высоких и критических; средние и низкие видно только вручную).
- **Куда класть код** (подробно — [`../CLAUDE.md`](../CLAUDE.md) › Конвенции):
  чистые функции → `app/utils/*` + юнит-тесты; реактивная логика → `app/composables/*`;
  UI → компоненты. Данные из API рендерим только через `{{ }}`, никакого `v-html`.
- **UI-правки сверяем с документацией Bitrix24 UI** (`b24ui`).
- **Тексты для пользователя** — по-русски, простыми словами. Если ожидается нажатие — пишем
  про нажатие. В ошибке должно быть понятно: **где** произошло, **что** случилось,
  **что делать дальше**.
- **Комментарии и JSDoc в коде** — по-английски; `.md` и пользовательский текст — по-русски.

### Команды

```bash
pnpm dev            # дев-сервер
pnpm check          # lint + typecheck + test — гонять перед пушем
pnpm test           # только тесты (быстро: pnpm test --project unit)
pnpm generate       # сборка статики (то же гоняют CI и Dockerfile)
pnpm preview        # посмотреть собранную статику локально
pnpm screenshots    # скриншоты роут × вьюпорт × тема (см. §2.2)
pnpm og:snapshot    # регенерация public/og.png из scripts/og.svg
pnpm rates:snapshot # регенерация public/rates-fallback.json
```

## 2. Проверка

Три уровня. Первые два обязательны всегда, третий — перед релизом в Маркет.

### 2.1. Автотесты (`pnpm check`)

Покрыто: чистые функции (`app/utils/*`), конфиг, директива автоповтора, composables и
страницы (проект `nuxt`), паритет локалей, штампы документов, список зон в правилах
безопасности. Портал Bitrix24 и живая Метрика в автотестах **не** проверяются — SDK замокан.

### 2.2. Глазами (`pnpm screenshots`)

Мини-инструмент для скриншотов: снимает роут × вьюпорт × тему (12 PNG, 375×812 и 1280×900)
уже установленным Chromium. Эталонов и сравнения нет — это «свериться глазами», поэтому
**в CI не гоняется** и прод не трогает. Результат — в `screenshots/` (в git не попадает).

**Снимать нужно собранную статику, а не дев-сервер** — именно она уезжает в прод:

```bash
pnpm generate && pnpm preview   # в одном терминале
pnpm screenshots                # в другом
```

Переменные: `BASE_URL` (по умолчанию `http://localhost:3000`), `PLAYWRIGHT_CHROMIUM_PATH` —
на macOS и Windows путь к Chromium может не определиться сам, тогда задайте его явно.

Что смотреть: главная (светлая и тёмная, 375 и 1280), виджет `/widget/converter` (компактная
раскладка под узкий iframe), `/install` (вне портала снимок ловит экран мок-прогресса
«Application installation / Connecting to Bitrix24…» и свёрнутую «Diagnostics» — переход
на `/` происходит позже и в кадр не попадает).

### 2.3. Руками: то, что автотесты не могут

Нужен реальный портал Bitrix24 и валидный счётчик Метрики.

**Критично для релиза** (блокеры публикации):

| # | Что | Ожидание | ✓ |
|---|---|---|---|
| К1 | Открыть `/` | Строки валют заполнены, есть дата «на ДД.ММ.ГГГГ» | |
| К2 | Ввести сумму в BYN, затем в USD | Остальные валюты пересчитались в обе стороны | |
| К3 | Виджет в чате → «Вставить в чат» | В поле ввода чата вставлена **пропись** | |
| К4 | Установка приложения в портал | Прогресс → регистрация виджета → успех, без белого экрана | |
| К5 | `make prod-smoke-external` | `200`, валидный TLS | |

**Виджет в чате и установка** — ломаются от версии портала, поэтому отдельным списком:

| # | Что | Ожидание | ✓ |
|---|---|---|---|
| В1 | Рендер виджета в панели над полем ввода | Компактный конвертер: строки валют, пропись BYN/RUB | |
| В2 | Переключатель регистра «аб/Аб» | Первая буква прописи меняет регистр | |
| В3 | Копирование (кроме мобильного приложения) | Сумма или пропись в буфере | |
| В4 | Мобильное приложение Б24 | Контролы крупнее, кнопки копирования скрыты (в мобильном нет доступа к буферу) | |
| В5 | Виджет при недоступном API курсов | Сообщение об ошибке, без падения | |
| В6 | Узкий попап, **реальный браузер с классическим скроллбаром**, **выделить сумму** | Нет горизонтальной полосы прокрутки и сдвига вправо | |
| У1 | Имя виджета на 2–3 языках портала | На плашке виджета имя приложения на языке портала | |
| У2 | Повторная установка | Старые привязки чистятся, дублей нет | |
| У3 | Прервать установку / сбой | Показана кнопка повтора, а не белый экран | |
| У4 | Открыть `/install` вне портала | Мок-прогресс, затем переход на `/` | |
| У5 | Главная, открытая как приложение портала | Заголовок фрейма выставлен, фрейм подгоняется под контент, блок «Помог курс?» скрыт | |

**Остальное — важное, но не блокирующее:**

- *Конвертер:* удержание +/− (автоповтор, значение не выходит за 0…максимум), копирование
  строки (в буфере чистое число с точкой), пропись BYN/RUB, формула и метка квартала,
  обновление курсов, пустое поле, ноль и максимум, мусорный ввод.
- *Ошибки:* открыть `/` без сети → красный блок с понятным текстом, без падения; кэш в
  пределах 12 ч не ходит в сеть; помесячная валюта (RSD) может быть пустой — страница жива;
  протухший кэш перезапрашивается (проверить можно, подделав отметку времени в кэше
  браузера на срок больше 12 часов назад).
- *Темы и адаптив:* тема сохраняется между визитами без мигания; авто-тема по системной;
  375px без горизонтального скролла; Tab-навигация и скринридер.
- *Промо:* карточка Маркета видна на обычном сайте и **скрыта** в портале; карточка
  доработки видна всегда; QR по удержанию.
- *Цели Метрики* — пройтись в отчёте Метрики по списку из
  [`PROJECT_MAP.md`](PROJECT_MAP.md) §4 (только на обычном сайте — в портале статистика
  выключена). Отдельно: показатели скорости `web_vitals_*` появятся, только если
  **повзаимодействовать со страницей** (нужно для замера отклика) и затем **закрыть или
  скрыть вкладку** — иначе замер не отправится.
- *Прод-дым:* нет ошибок правил безопасности в консоли; в подвале «сборка `<sha>`» ведёт на
  актуальный коммит.

## 3. PR, ревью и мерж

1. **PR в `main`.** В теле — проблема и что сделано, ссылки на issue (`Closes #N`).
2. **Проверяющие.** Каждый PR смотрят несколько независимых ревьюеров (для кода — до 5:
   корректность, тесты, безопасность и приватность, архитектура, тех-директор; для доков —
   точность против кода, потери информации, понятность, целостность ссылок, тех-директор).
   - **На излом:** проверяющий ищет дыру, а не подтверждает. Вердикт —
     **БЛОКЕРЫ / ЗАМЕЧАНИЯ / ЧИСТО**.
   - **Формат находки:** кто · что · почему · как исправить.
   - **Устранение:** блокеры обязательны; замечания — устранить либо обосновать отказ.
     После правок — перепроверка.
   - Смысл не в зелёной галочке: например, фикс горизонтального скролла виджета оказался
     в родительском layout, а не там, где правил автор — это нашли именно проверяющие.
3. **Мерж — только когда `ci` и `docker-build` зелёные.** Метод — squash, в заголовке номер PR.
   Решение о мерже за владельцем; агент доводит PR до зелёного CI и мержит только по явному
   разрешению.
4. **Отдельного срочного пути нет** — прод-инцидент идёт тем же циклом; быстрый выход —
   откат ([§7.2](#72-обновление-и-откат)).

### Конвенции документации

- **Один источник правды.** Между документами — перекрёстные ссылки, а не копипаста.
  Скопированный в два места факт однажды разойдётся.
- **Штамп ревью.** Каждый `.md` в корне и в `docs/` несёт строку
  `> Last reviewed: YYYY-MM-DD` блок-цитатой сразу под заголовком H1. Ключ `Last reviewed` —
  всегда по-английски (технический маркер, ищется одним grep). Дату бампим только при
  содержательном изменении, не при косметике. Наличие штампа проверяет
  `tests/mdReviewStamp.test.ts` (`reporting-kit/` исключён — у него свой процесс).
- **Язык.** Пользовательский текст и `.md` — по-русски; комментарии и JSDoc в коде — по-английски.

## 4. Сборка и деплой

```
push в main
  └─ GitHub Actions job `ci` (зелёный?) → job `deploy`
       └─ docker build → push в ghcr.io/bx-shef/currency-converter:latest + :sha-<коммит>
            └─ Watchtower на сервере (~5 мин) подхватывает latest
                 └─ контейнер пересоздаётся за общим nginx-proxy (TLS Let's Encrypt)
```

- **CI** (`.github/workflows/ci.yml`): job `ci` (install → `nuxi prepare` → lint → test →
  typecheck → `nuxt generate`) на push и PR; job `docker-build` на PR (собирает прод-образ
  **без** push — ловит поломку Dockerfile до прода, работает и на Dependabot-PR). Кэш сборки
  на PR — только на чтение, чтобы PR-сборки не вытесняли кэш основной ветки.
- **Красный `ci` блокирует деплой** — образ не попадёт в реестр.
- **Теги:** `latest` (его слушает Watchtower) + `sha-<коммит>` (неизменяемый, нужен для отката).
- Два быстрых пуша в `main` выстраиваются в очередь — уже идущая выкладка не обрывается,
  полу-выложенный тег хуже ожидания.

### Что собирается в образ

Прод-образ — `nginxinc/nginx-unprivileged` (работает не от root, слушает `:8080`). Сборка
**валится**, если что-то из этого не сошлось:

- хэши безопасности не подставлены (плейсхолдер `__CSP_SCRIPT_HASHES__` остался в `nginx.conf`);
- `nginx -t` не проходит;
- `public/og.png` не попал в вывод.

Правила безопасности отдаются **без** разрешения встроенных скриптов: два служебных скрипта
Nuxt разрешаются по их хэшам, которые `scripts/csp-hashes.mjs` считает из собранного HTML.
**Любой новый встроенный скрипт сломает страницу** — выносить в `public/*.js` (как сделано
с Яндекс.Метрикой).

## 5. Установка в портал Bitrix24

Приложение работает в двух режимах: обычный сайт и iframe внутри портала.

1. Портал открывает `/install` **методом POST**, поэтому в nginx стоит
   `error_page 405 =200 $uri;` — без него статика отвечает «405 Not Allowed» и пользователь
   видит белый экран.
2. `/install`: подключение к порталу → чистка старых привязок → регистрация плейсмента
   `IM_TEXTAREA` (панель над полем ввода чата) на обработчик `/widget/converter` →
   завершение установки. Имя виджета берётся из `app.title` **всех** локалей в момент
   установки.
3. Дальше пользователь открывает виджет в чате и жмёт «Вставить в чат» — пропись уходит
   в поле ввода.

Требования к правилам безопасности: `frame-ancestors` и `connect-src` в `nginx.conf` должны
разрешать облачные домены Б24 (`*.bitrix24.<зона>`, ровно 22 зоны). Список **зеркалится**
между двумя директивами, точный набор проверяет `tests/nginxCsp.test.ts`. Синхронизируется
вручную — Б24 добавляет регионы; **порталы на собственном домене добавляют себя сами**,
иначе iframe и REST-вызовы не работают.

Полный процесс установки автотестами не проверить (нужен портал) — только руками,
см. [§2.3](#23-руками-то-что-автотесты-не-могут) К3–К4 и У1–У5.

## 6. Публикация в Маркете Bitrix24

Гейт — это проверка-заслон: не прошли, не публикуем. Цель — не выпустить в Маркет то, что
сломано в портале.

| # | Гейт | Как проверить | ✓ |
|---|---|---|---|
| 1 | Автопроверки зелёные | `pnpm check` | |
| 2 | Прод задеплоен и жив | `make prod-smoke-external` → `200` | |
| 3 | Визуальная проверка | `pnpm screenshots`, просмотреть `/`, `/widget/converter`, `/install` в свете и тьме на 375/1280 | |
| 4 | Ручной прогон в портале | [§2.3](#23-руками-то-что-автотесты-не-могут) К3–К4 и У1–У5 | |
| 5 | Версия сборки | в подвале «сборка `<sha>`» ведёт на актуальный коммит | |
| 6 | `MARKETPLACE_URL` актуален | указывает на опубликованный листинг | |
| 7 | Имя приложения на всех языках | `app.title` во всех `i18n/locales/*.json` | |
| 8 | Правила безопасности разрешают облако Б24 | `frame-ancestors`/`connect-src` в `nginx.conf` | |
| 9 | Приватность актуальна | [`PROJECT_MAP.md`](PROJECT_MAP.md) §4 — для карточки Маркета и вопросов о данных | |

**Порядок:** смержить в `main` → дождаться авто-деплоя (~5 мин) или `make prod-redeploy` →
пройти гейты 1–9 → обновить листинг в кабинете разработчика (описание, скриншоты, версия) →
после публикации ещё раз пройти гейт 4, но уже установкой **из Маркета** на тестовом портале.

### Случаи, когда порталам нужна переустановка

- **Смена `app.title`** — имя виджета фиксируется в момент установки.
- **Смена домена или `NUXT_PUBLIC_SITE_URL`** — адрес обработчика абсолютный, нужна
  пересборка образа и переустановка.
- **Крупное обновление `@bitrix24/b24jssdk`** — работу SDK автотесты не покрывают,
  обязателен ручной прогон в реальном портале.

**Известные ограничения** публикацию не блокируют, но задокументированы: #124, #136, #138 —
подробности в [`FUTURE.md`](FUTURE.md).

## 7. Эксплуатация

### 7.1. Регулярный мониторинг

| Что | Как проверить | Норма |
|---|---|---|
| Доступность снаружи | `make prod-smoke-external` | `200`, валидный TLS |
| Контейнер жив | `docker ps` (проверка каждые 30 с) | `Up (healthy)` |
| TLS-сертификат | команда ниже | обновить, если **меньше 14 дней** |
| Свежесть деплоя | `docker inspect currency-converter --format '{{index .Config.Labels "org.opencontainers.image.revision"}}'` | коммит совпадает с последним в `main` (то же видно в подвале сайта: «сборка `<sha>`») |
| Watchtower | `docker logs watchtower --tail 20` | периодические «Session done» |
| Уязвимости в библиотеках | `pnpm audit` | **0**. CI ловит только важные (высокие и критические) — средние и низкие видно лишь этой командой. Чинится планкой в `pnpm.overrides` (см. [`PROJECT_MAP.md`](PROJECT_MAP.md) §3.6) |
| Диск | `docker system df` | логи ограничены (10 МБ × 3); при росте — `docker image prune -f` |

```bash
# срок действия сертификата
echo | openssl s_client -connect $DOMAIN:443 2>/dev/null | openssl x509 -noout -enddate
```

TLS продлевается автоматически; руками вмешиваемся, только если продление **не** происходит.

**Здоровье приложения** видно по целям Метрики (только на обычном сайте): рост
`rates_load_failed` = проблема с `api.nbrb.by`; `rates_fallback_used` = сайт НБ РБ лежит и
людям показывается сохранённая копия; `web_vitals_*` = скорость.

### 7.2. Обновление и откат

- **Обычное обновление** — автоматически: мерж в `main` → CI выкладывает образ → Watchtower
  подхватывает за ~5 мин. Форсировать: `make prod-redeploy`.
- **Откат:** `make prod-rollback TAG=sha-<коммит>` — поднимает конкретный неизменяемый образ
  и проверяет, что он отвечает. Watchtower такой тег не трогает. Вернуть авто-обновление —
  `make prod-redeploy`.
- **После отката или редеплоя — обязательно `make prod-smoke-external`** (проверяет весь путь
  снаружи: DNS → прокси → TLS → приложение, чего внутренняя проверка не ловит).

Остальные команды: `make prod-up` / `prod-down` / `prod-pull` / `prod-smoke` / `logs`.

### 7.3. Инциденты

| Симптом | Первая гипотеза | Что делать |
|---|---|---|
| `502` от nginx-proxy | контейнер не в той docker-сети, либо прокси шлёт не на тот порт | Различить две причины — командами ниже |
| Белый экран в портале, `405` или смешанный контент | пропал `error_page 405 =200 $uri;` или `absolute_redirect off;` | проверить `nginx.conf` в образе, пересобрать |
| TLS не выдан или не продлён | DNS не резолвится или сработало ограничение Let's Encrypt | `docker logs <acme-companion>`; `dig +short $DOMAIN`; проверить `LETSENCRYPT_EMAIL` |
| Watchtower не обновляет | нет `DOCKER_API_VERSION` или метки на контейнере | `docker logs watchtower`; метка `com.centurylinklabs.watchtower.enable=true` |
| Курсы не грузятся у всех | `api.nbrb.by` недоступен | Внешняя проблема НБ РБ. Первую загрузку спасает `public/rates-fallback.json` (бейдж «резервная копия»), вернувшихся — кэш браузера. Копия статична, обновляется `pnpm rates:snapshot` |
| Сборка или деплой красные | см. Actions: `ci` → `deploy` | Частое: нет lockfile для кэша; мажорный бамп Node; пропавший файл `og.png` |

**Разбор 502 — две гипотезы и как их различить:**

```bash
# 1) оба контейнера в одной сети?
docker network inspect <сеть>
docker inspect <контейнер-приложения> | grep -A3 Networks

# 2) на какой порт прокси реально шлёт? Строки "using port" / "server <IP>:<порт>"
docker exec <контейнер-прокси> grep -A6 '<домен>' /etc/nginx/conf.d/default.conf
# должно совпадать с `listen` в nginx.conf образа — у нас 8080
```

Частая первопричина второго случая — **устаревший `docker-compose.prod.yml` на сервере**:
после PR, менявшего порт или сеть, файл надо перекачать (`curl -fsSLO`, см.
[§0.3](#03-сервер)) и сделать `make prod-up`.

**Логи:** приложение — `make logs`; Watchtower — `docker logs watchtower`; сертификаты —
`docker logs <acme-companion>`. Ротация 10 МБ × 3, диск не забьётся.

### 7.4. Чего не делать

- **Не поднимать nginx-proxy второй раз**, если он уже стоит — порты 80/443 заняты, упадёт
  весь сервер вместе с соседними сайтами.
- **Не пересоздавать docker-сеть** с «правильным» именем без подтверждения владельца.
- **Не выкладывать образ только с тегом `latest`**, без `sha-<коммит>` — без него нельзя
  откатиться.
- **Не класть `.env.prod` в git** и не клонировать репозиторий на сервер.
- **Не мержить PR самостоятельно** без явного разрешения владельца.
- **Не трогать пины версий** watchtower / nginx-proxy / acme-companion — у них доступ к
  управлению Docker, плавающая версия там = дыра в безопасности. Пины сторонних GitHub
  Actions обновляет Dependabot.

## 8. Грабли, за которые уже платили

Коротко, чтобы не наступить второй раз.

| # | Грабля | Как правильно |
|---|---|---|
| 1 | Имя docker-сети nginx-proxy на серверах разное (`proxy-net`, `nginx-proxy`, `webproxy`) | Не угадывать — смотреть `docker network ls`; в compose помечать `external: true`. Не совпало → 502 |
| 2 | `default`-сеть в compose приложения | Убрать: без явного `networks:` контейнер окажется в двух сетях |
| 3 | `LETSENCRYPT_EMAIL` продублирован в compose приложения | Он живёт глобально рядом с nginx-proxy. В приложении оставлять только `VIRTUAL_HOST`, `VIRTUAL_PORT`, `LETSENCRYPT_HOST` |
| 4 | Безымянные контейнеры | Задавать `container_name` каждому сервису, включая watchtower и nginx-proxy — иначе `docker logs <имя>` из этой инструкции не работает |
| 5 | Watchtower по умолчанию обновляет **все** контейнеры хоста | `--label-enable` + метка на нашем сервисе |
| 6 | Watchtower молча не работает | Нужен `DOCKER_API_VERSION=1.47`: по умолчанию он говорит на старой версии API, которую свежий Docker уже не принимает |
| 7 | Публичные переменные Nuxt через `environment:` в compose | Не сработают — они запекаются при сборке, нужны аргументы сборки ([§0.2](#02-переменные-приложения)) |
| 8 | `docker compose up`/`pull` без `--env-file .env.prod` | Переменные не подхватятся. В Makefile это прописано, при ручном запуске — помнить |
| 9 | Выкладка образа падает с отказом в доступе | Workflow нужны права `packages: write`; отдельный токен не требуется |
| 10 | Приватный репозиторий → образ тоже приватный | Понадобится вход в реестр на сервере (токен с правом чтения пакетов) либо файл авторизации для Watchtower. Сейчас репозиторий публичный, вход не нужен |
| 11 | Права CI шире необходимого | Прописывать `permissions: { contents: read }` явно даже на проверочных задачах |
| 12 | Заголовки безопасности только на внешнем прокси | Дублировать их **внутри образа** — на случай мисконфигурации внешнего слоя |
| 13 | non-root nginx не может слушать `:80` | `listen 8080` + `VIRTUAL_PORT: 8080`; иначе 502 |
| 14 | За TLS-прокси внутренний nginx строит редиректы со своим портом | `absolute_redirect off;` — иначе браузер получает адрес с внутренним портом и по http, а в HTTPS-iframe портала это смешанный контент, и виджет молча не грузится |
| 15 | Б24 открывает обработчик методом POST, статика отвечает `405` | `error_page 405 =200 $uri;` — странице не нужно тело запроса, контекст портала приходит другим путём |
| 16 | Правила безопасности ломаются на любом новом встроенном скрипте | Выносить скрипты в `public/*.js`; хэши считает `scripts/csp-hashes.mjs`, проверка в Dockerfile валит сборку |
| 17 | Логи контейнеров без лимита забивают диск | `max-size: 10m`, `max-file: 3` |
| 18 | Мажорный бамп Node ломает сборку | Node 25+ выкинул corepack из образов — держим базу на LTS `node:22-alpine`, Dependabot на мажоры Node не прыгает |
| 19 | Нет lockfile → кэш зависимостей в CI падает | `pnpm-lock.yaml` закоммичен до включения кэша |
| 20 | OG-картинка требовала тяжёлый inkscape в образе | `public/og.png` закоммичен, регенерация локально `pnpm og:snapshot` |
| 21 | DNS не готов до первого запроса сертификата | Let's Encrypt закеширует отказ на час — сначала DNS, потом запуск |
